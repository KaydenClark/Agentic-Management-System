# AMS site

The public presentation site for the AMS (Spec S-003), a Next.js app deployed on Vercel. Site work goes feature branch -> `dev` -> `main`; only the owner merges `dev` -> `main`.

## Build and test

Node.js 20 or later builds the site; `npm test` needs Node 21 or later (Node 22 is what the checks ran on). From `site/`:

```bash
npm ci
npm run build
npm test
```

`npm run build` is a plain `next build`. `npm test` runs `node --test "tests/**/*.test.mjs"` (Node's built-in runner; the glob is quoted so Node expands it, which needs Node 21 or later). The tests read the prerendered HTML in `.next/server/app/`, so run `npm run build` first and rebuild after each commit: the footer test compares the built SHA with the current commit.

`npm test` is browser-free and takes a few seconds. Besides the page tests it runs `tests/hygiene.test.mjs` over every file the site serves (prerendered HTML and RSC in `.next/server/app/`, client JS and CSS in `.next/static/`): no host path (`/home/`, `/Users/`, `C:\Users\`, `file:///` with a drive or host directory), Supabase secret or service-role key, JWT, API token, private key block, email address, reference to the private GPT_OS repository or agent session link; and no HTML or CSS resource (script, `<link>`, image, CSS `url()` or `@import`) loaded from a host other than Supabase or GitHub. The patterns live in `tests/hygiene.mjs`; its planted-fault cases plant into a copy of a built page.

Browser checks (needs Playwright with Chromium installed, resolved with `require("playwright")`; not a site dependency. axe-core is a devDependency and is injected from `node_modules`, never a CDN):

```bash
npm run check:browser                                  # starts `next start` itself
node tests/browser.check.mjs --shots DIR               # also saves qa-<route>-<theme>-<width>.png
node tests/browser.check.mjs --url http://host:port    # check a running server instead
```

`tests/browser.check.mjs` reads every route from the build manifests (plus the not-found page), so a new page is covered without editing the check. Each route is opened at 375 px and 1280 px in light and dark and checked for: no horizontal scroll; an axe-core WCAG 2.x A/AA pass, contrast included (contrast axe cannot decide counts as a failure); Tab reaching every visible control, each with a visible focus indicator; nothing animating, transitioning or smooth-scrolling under `prefers-reduced-motion: reduce`; and every request going to the site, Supabase or GitHub. Requests to other hosts are recorded and aborted, so the check contacts no third party. It also keeps TK-001's home checks (theme follows the system, the toggle overrides and persists, fonts self-hosted) and checks each page's text with scripts disabled. Before the real pass it plants each fault into a live page (low contrast, a too-wide element, focus outlines removed, a control taken out of the tab order, a transition and an animation ignoring reduced motion, an external font) and fails if any check misses its fault. It exits non-zero on any failure.

## Shell

- `app/layout.tsx` wraps every route in `app/shell/Shell.tsx`: a top bar with the site title, the reading-order links and the theme toggle; the page in `<main>`; and the commit footer. Header, main and footer share one centered `.container` (`--container` in `app/theme/tokens.css`), a reading width that every block in `<main>` fills, so text, cards and the header share both edges; a wide page adds `.container-wide` (`--container-wide`). A page renders only its own content.
- Top bar: the wordmark over its tagline and an icon-only theme toggle on the first row; the reading-order links on the row below, each stretched so the row spans the column. Below 768 px the links wrap three a row.
- `app/nav.ts` is the one reading-order list; order is reading order. Add an entry only for a route that exists.
- Typography uses rem-based shared sizes (18px body, 17px controls, 16px navigation and 15px supporting text at the default root size), generous line spacing and responsive titles. Emergency word wrapping supports narrow-screen text reflow. The Start hub scales with text and becomes an AMS-and-parts list on phones, keeping labels separate from its explanatory caption.
- `app/theme/tokens.css` is the only file with color, type and spacing values (Color system v2.2 from the owner's Grilling Board Redesign canvas). Everything else uses `var(--token)`; `tests/tokens.test.mjs` enforces it.
- Theme: follows the system; the toggle overrides it and is stored in `localStorage` (`ams-theme`); a first-party inline script in `<head>` reapplies the stored choice before first paint.
- Press and hover: buttons (the theme toggle, the toy's controls) shrink slightly while pressed (`--press-scale`, `--motion-press`, `--ease-out`), and their hover styles apply only under `(hover: hover) and (pointer: fine)`, so a tap leaves no stuck hover. Under reduced motion the press has no transition.
- Footer SHA: `next.config.ts` fixes it at build time from `VERCEL_GIT_COMMIT_SHA`, else `git rev-parse HEAD`, else `unknown`.
- Fonts (IBM Plex Sans, IBM Plex Mono, Zilla Slab) are self-hosted through `@fontsource`; the site makes no third-party requests.

## Page hashes

The public site shows no review state: no page carries a draft, approval or review banner. Owner review of pages belongs to the owner-facing S-005 Grill Board, which binds each review to the page's content hash; nothing about it changes what a public page shows.

- **Content hash** (the S-005 page-hash contract): `sha256:` + SHA-256 hex of the canonical content of the built page's `<main id="main">`. Drop `<script>`, `<style>`, comments and every subtree whose element carries `data-review-mark` or `data-review-exclude` (no page carries `data-review-mark`; the contract keeps it); take each text node and each `href`, `src` and `alt` value in document order (attributes as written, before the element's content), with character references decoded; join with single spaces, collapse ASCII whitespace (tab, LF, FF, CR, space) to one space and trim; encode UTF-8. The footer commit is outside `<main>`, so a rebuild alone changes no hash. The back/forward links (`PageOrder`) are shell navigation and carry `data-review-exclude`, so adding a page to the reading order changes no other page's hash; mark live regions the same way. Code: `scripts/page-hash.mjs`; vectors with independently computed hashes: `tests/fixtures/page-hash/vectors.json`.
- **Current hashes:** `npm run page-hashes` (after a build) prints each page's route and hash; `--json` prints JSON.
- **Recording an owner review:** reviews come only from the owner, in chat until the Grill Board exists (DDR-000X); an agent never creates one. Rebuild, run `npm run page-hashes`, and have the owner review the exact route and hash. The record is a dated note of the approval itself: who approved, the date, the channel, and each route and hash approved, written in paraphrase and never quoting the owner. It belongs with the Grill Board's records (S-005), never on the public site.
- **Tests:** `tests/page-hash.test.mjs` (in `npm test`) checks the vectors; that every built page has a hash; that the hash ignores a review mark, the footer commit, scripts and `data-review-exclude` regions, and changes when one character of content changes; that `npm run page-hashes` prints every page; and that no built page shows review state (a `data-review-mark` element, a note announcing draft, approval or review, or not-approved wording), after catching each of those planted into a built page.

## Theme token check

The theme block of `app/theme/tokens.css` (light, manual dark, the system-dark `@media` rule and the `.tone`/`.h-*` mixes) is generated from `../grill-board/theme/tokens.json`, the recorded Grill Board theme ([DDR-000Y](../workbench/docs/ddr/000Y-the-grill-board-theme-follows-the-grilling-board-redesign-artifact.md)), and sits between the `BEGIN theme tokens` and `END theme tokens` markers. To change a color, edit `tokens.json`, then run `npm run tokens:gen` (`node scripts/gen-tokens.mjs --write`; without `--write` it prints the block). `tests/tokens-json.test.mjs` fails `npm test` unless the block equals the generator's output byte for byte, each marker appears once, and nothing outside the markers declares a recorded token or holds a color-like value. Type and spacing tokens are hand-written after the block and are not in `tokens.json`, so they are not compared; `tests/tokens.test.mjs` still keeps every literal inside `tokens.css`. Vercel builds with root directory `site/`, so the check runs in the local `npm test` only.

## Tour pages (`/start`, `/why`, `/how-it-works`, `/glossary`, `/about`)

Every tour page opens with a `<p data-opener>` plain-language summary; any term from the jargon list in `tests/tour-helpers.mjs` used there must be a `<dfn>` or link to an on-page id or the Glossary. Every claim links the committed record it comes from on GitHub (`blob/dev/...`).
- The site quotes no one, the owner included, and never shows the owner's own instructions to agents as examples: a point from the owner is paraphrased in plain prose, without quote marks, and links the committed record it comes from, and any example request on a page is invented. `tests/tour-inventory.test.mjs` fails a tour page holding a `<blockquote>`, a `<q>`, words in quote marks or a `data-owner-quote` figure, and fails any built page carrying `data-owner-quote`; both checks run on planted faults first.
- About is the canonical introduction at `/start`, retaining its existing section anchors, diagrams, toy and quickstart. `/about` renders that same content in the same navigation position, with `/start` as the primary link; it is not a second introduction. Home directs readers to the subjects; Why explains the problem and intended benefits; How it works owns records, governance, the Grill Board explanation and the historical example. Screen 3 shows Kayden's skills by Workbench stage from `app/start/skills.mjs` (typed by `skills.d.mts`; main-flow skills solid and in order, the rest outlined, no hue); `tests/start-flow.test.mjs` checks every stage and skill appears in it, main-flow skills marked and ordered. The rest renders from `app/start/flow.mjs` (plain JavaScript typed by `flow.d.mts`, so `npm test` needs no TypeScript loader; the lifecycle stages, who holds each, their sources, and the owner/orchestrator split). The toy (`app/start/Toy.tsx`) is a client component that keeps state in memory only; before scripts run it renders every stage as a numbered list (`data-toy-fallback`). Its only hues are the four holder signals through the `.tone` mixes: `h-owner`, `h-agent`, `h-returned`, `h-none` for done. `tests/start-flow.test.mjs` checks every stage appears in the diagram and the fallback, the returned branch uses the returned token, no other hue is used and the toy source has no network or storage API; `npm run check:browser` plays the toy to its last stage by keyboard alone with zero requests and unchanged storage, and takes the return branch by keyboard with focus kept on the toy (`--shots` adds `start-toy-NN-<stage>.png` at 1440 px dark).
- Why (`app/why/`) and Glossary (`app/glossary/`) are S-003 TK-003. They share `app/tour/Source.tsx` (the source link) and `app/tour/tour.module.css`.
- The project identity, license and build explanation now live in the unified About introduction (`app/start/`); old `/about#holds`, `#license`, `#status` and `#built` links remain useful. `tests/about.test.mjs` keeps its license line true: the page must say the LICENSE file is empty exactly while it is, so applying the license text fails the test until the page is updated.
- Glossary: `app/glossary/glossary.json` is generated from the repository's `GLOSSARY.md`, the one home of the project's terms. After editing `GLOSSARY.md`, run `npm run glossary:gen` (`node scripts/gen-glossary.mjs --write`; without `--write` it prints the JSON) and commit both. `tests/glossary.test.mjs` fails `npm test` unless the JSON equals the generator's output byte for byte and, read independently from `GLOSSARY.md`, every term is a `<dt>` with an id on the built page followed by its definition word for word, with no term the file lacks.
- Quickstart: the last screen of Start here (`#quickstart`), not a page of its own. Following S-003, it is a reading route with nothing to install, no credentials and no commands: the introduction, one real Spec and Task (`/how-it-works#example`), the toy and the Skills wiki, then the RSI results and the limits on Why, each saying what it teaches. It then tells the reader to use the `setup-workbench` skill to set up a Workbench, sourced to `workbench/docs/SKILLS.md`, the README and the manifest's `skillPolicy`; the skill is in the owner's personal catalog, not this repository, so the step links its `/skills/setup-workbench` article. The earlier `/quickstart` page and its command replay test are gone with the commands they guarded.
- `app/shell/PageOrder.tsx` puts back and forward links (`rel="prev"`/`rel="next"`) at the end of every page in `app/nav.ts`; a new page gets them by being added to `nav.ts`.
- Tests (`npm test`): `tests/tour-inventory.test.mjs` (every tour page in `TOUR` in `tests/tour-helpers.mjs` exists, openers, placeholders, no quotes, GitHub links name existing files) and `tests/tour-links.test.mjs` (reading order, back/forward links on every page, no orphan page, internal links resolve). A built page outside the reading order passes the orphan rule only as a child one level under a reading-order page (`/skills/<name>` under `/skills`) that its parent links and that links back to it. Each runs planted-fault self-tests first.
- Browser check at 375 px, both themes, every page in the reading order: `node tests/tour-375.check.mjs [--shots DIR]` (needs Playwright with Chromium; screenshots are `tour-<page>-<theme>-375.png`).

## RSI charts (`/rsi`)

The chart page lives in `app/rsi/`. `page.tsx` is a server component: `supabase.ts` reads S-006's `rsi_runs` and `rsi_results` tables with plain `fetch` against Supabase REST (`/rest/v1/<table>?select=...&is_test=is.false`, `apikey` and `Authorization` headers), at build and on revalidation every five minutes. It needs `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (publishable key; never commit it). Missing configuration, failed requests and malformed rows render unavailable, never "no trials"; successful reads carry their timestamp. Null metrics remain unknown and never become a partial total.

`seriesViews(data)` in `data.ts` groups rows per task and per version, held-out and dev apart, one series per arm, provider, model and effort (a model change starts a new series), drops any test row, and marks regressions (a lower share of passing graded trials than the prior version in the series; a count comparison, not a significance test), and, by S-002's `rsi_runs.detail` contract (no extra columns; a missing key is absent): variants (`detail.variant` true), removed versions (`detail.disposition` `remove`; `retain` and `revise` are shown as the round's disposition), fired stop rules (state `stopped` with `detail.stop_rule` in plain words and `detail.stop_note`) and failed runs (state `failed`, marked apart from stops). `detail.version` is shown as the candidate label; the three commits stay the version's identity. `view.tsx` renders it: every number links to the list of exactly its rows, each row with its strength label and source.

Tests, all in `npm test`: `tests/rsi-empty.test.mjs` checks the built page's empty state with planted faults; `tests/rsi-rows.test.mjs` renders `view.tsx` on the labeled fixtures in `app/rsi/fixtures/cases.ts` (link coverage, model change, regression, variant/removed/stop rule, test rows, empty and unavailable) through a TypeScript loader hook (`tests/tsx-hooks.mjs`), and checks the Supabase read with a stubbed `fetch`; `tests/rsi-key.test.mjs` fails if any served file holds a publishable key. To check a live read locally, export both variables in your shell, run `npm run build`, and confirm `.next/server/app/rsi.html` has no `data-load-note`.

`repair-data.ts` is a separate safe snapshot of published S-011 evidence, rendered by `repair.tsx`: development predicate counts, the first failed/incomplete audit and the documentation failure chronology, each linked to exact public records. It is not a raw assessment reader or synthetic Supabase trial data. `rsi-repair.test.mjs` checks counts, source links, privacy and explicit limits; missing final-bundle, qualification, installation/use and useful-benefit evidence remains pending. Empty-state planted faults use an explicit successful-empty fixture, while a separate build check verifies unavailable reads never claim emptiness.

## Skills wiki (`/skills`, S-008)

Site-written articles on Kayden's skills, one per skill on the chart, grouped by Workbench stage. The skills repository is private: the site publishes articles written for it, never skill files, and never links it.

- **Files.** One article per chart skill in `content/skills/<name>.md`, `<name>` the skill's folder name in the skills repository (`align-concept`, never `grill-me`). The format is the S-008 article contract: front matter `name`, `summary` (at most 160 characters), `pin`, `credit` (`original` or `adapted`), `credit_text`, and `credit_license` for an adapted skill; then the `##` sections What it does, When to use it, Example request, What it requires, What it does not authorize, any skill-specific sections, FAQs (three to six `###` questions ending in `?`), It's working when (one `-` list) and Where it fits in the workflow (names its stage). An article never states its stage: stage and order come from `app/start/skills.mjs`, the chart's one encoding.
- **Markdown.** `app/skills/markdown.mjs` parses exactly the contract's subset (`##`/`###` headings, paragraphs, one-level `-` and `1.` lists, pipe tables with a header row, `>` blockquotes, ``` fences; inline code, bold, italic and links; a backslash escapes punctuation) and throws, naming file and line, on anything else: `#` or `####` headings, raw HTML, images, footnotes, reference links, nested lists, `_` emphasis and the rest. `app/skills/content.mjs` loads the folder and refuses, naming the file, a front matter or section-order breach, a non-chart name, a wrong pin, an adapted skill labeled original, or a link other than `/skills/<name>` for a chart skill, `/skills#<stage>`, a site route or a public `https://` URL. Both are plain `.mjs` typed by `.d.mts`, so the tests import them; `app/skills/Markdown.tsx` renders the tree as React elements, so no raw HTML reaches a page. No Markdown dependency.
- **Pages.** `/skills` (`app/skills/page.tsx`) lists the seven stages in chart order, each with an id anchor, its gloss and note; main-flow skills first, numbered and solid, then the skills also used, outlined; each entry links its article. `/skills/<name>` (`app/skills/[name]/page.tsx`) is generated for every content file and nothing else (`dynamicParams = false`): stage label linking `/skills#<stage>`, the name as title, the summary as lead, the sections, then the credit line and `Skills commit fb7ad23` (full SHA in `title` and `data-pin`). Back and next links in index order sit in a `data-review-exclude` nav, so adding an article changes no other article's hash. Tables reflow at 375 px (fixed layout, wrapping cells) and code blocks wrap, so neither scrolls.
- **Tests (`npm test`).** `tests/skills-markdown.test.mjs`: the fixture articles in `tests/fixtures/skills/` load, and each unsupported syntax and contract breach is refused. `tests/skills-wiki.test.mjs` over the build: article shape, coverage (the content files are exactly the 39 chart skills, the Spec's count per stage; no `grill-me`/`grill-with-docs`; every stage has an article), the index (every article under its stage, main flow first in order, each linked), stage labels, credit and pin, no page saying a skill was used to build the site (and no `data-used` mark), and wiki links resolve with nothing linking the private skills repository. Each runs planted-fault self-tests first. Coverage stays red until every chart skill has its article.
- **Source check (not in `npm test`; the skills repository is private and absent in CI).** `npm run check:skills-source -- --skills DIR [--content DIR]`, DIR a checkout of the skills repository: checks each article has a skill folder (`<name>/SKILL.md`) there and, when DIR is a git checkout, that its HEAD is the pin; then flags any run of 10 or more consecutive normalized words an article (summary or section) shares with any file in its skill's folder, printing article, section, word offset and skill file but never the words. A flagged run may be an allowed short quoted term or the skill's description phrase; a reviewer decides. It runs its self-test first (`tests/fixtures/skills-source/`, also run by `tests/skills-source.test.mjs` in `npm test`) and exits 1 on any finding.

The current article source pin is published catalog main `fb7ad23c963e183b930b23bc5fdf4d309dff292a`. The refresh checked changes from the prior pin, including referenced methods and setup assets; destination/history separation is reflected in affected articles. The handoff article explicitly distinguishes the still-published catalog method from AMS's local-only session-note boundary. Unmerged repair candidates are not described as completed methods.
